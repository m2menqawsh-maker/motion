# نظام ضغط السياق (Context Compaction)

## 🔴 المشكلة
في المحادثات الطويلة ومشاريع إنتاج الفيديو، يتراكم السياق بشكل كبير (سجل المحادثة، محتوى الملفات المقروءة، وسجلات الخطوات السابقة). هذا يؤدي إلى:
1. بطء شديد في استجابة الوكيل (Agent Freezing).
2. نسيان القرارات القديمة أو تجاوزها بسبب زحام السياق.
3. استهلاك غير مبرر للرموز (Tokens).

## 💡 الحل: كيف يعمل النظام؟
يعتمد النظام على إنشاء "ملخص جلسة" (Session Digest) مضغوط لا يتجاوز 100 سطر. هذا الملخص يحتفظ فقط بالمعلومات الحاسمة:
- **القرارات المعتمدة:** ما تم الاتفاق عليه مع المستخدم ويجب الالتزام به.
- **القرارات المرفوضة:** ما تم اقتراحه سابقاً ورفضه المستخدم (لمنع تكرار الاقتراح).
- **الحالة الحالية:** المرحلة الحالية للمشروع وحالة المشاهد.
- **المشاكل المحلولة:** لتجنب الوقوع في نفس الخطأ مرتين.

الوكيل يقرأ هذا الملخص القصير في بداية الجلسة بدلاً من قراءة السجل الكامل، مما يضمن احتفاظه بالذاكرة وتجنب التعليق. يتم تخزين البيانات الهيكلية في `.session_state.json` ويتم توليد `session_digest.md` منها.

## 🛠️ الأوامر المتاحة (CLI)

1. **توليد الملخص (Compact):**
   ```bash
   python scripts/context_compactor.py compact <project_id>
   ```

2. **إضافة قرار معتمد:**
   ```bash
   python scripts/context_compactor.py add-decision <project_id> "استخدام خط Alexandria للعناوين" --status approved
   ```

3. **إضافة قرار مرفوض:**
   ```bash
   python scripts/context_compactor.py add-decision <project_id> "استخدام الشاشة المنقسمة" --status rejected
   ```

4. **تحديث المرحلة الحالية:**
   ```bash
   python scripts/context_compactor.py set-phase <project_id> "build_scene_3"
   ```

5. **إضافة ملاحظة تقنية أو حل مشكلة:**
   ```bash
   python scripts/context_compactor.py add-note <project_id> issue_resolved "مشكلة BOM: تم تنظيف الملف عبر إزالة \uFEFF"
   ```

6. **عرض الملخص الحالي:**
   ```bash
   python scripts/context_compactor.py show <project_id>
   ```

## 🤖 متى يجب على الوكيل تشغيل هذه الأوامر؟

- **عند بداية أي جلسة أو مرحلة جديدة:** اقرأ `session_digest.md`. إذا لم يكن موجوداً، شغّل أمر `compact`.
- **فور اتخاذ قرار هام مع المستخدم (مثل الموافقة على الخطة أو أسلوب الحركة):** شغّل أمر `add-decision --status approved`.
- **فور رفض المستخدم لاقتراح معين:** شغّل أمر `add-decision --status rejected`.
- **عند الانتقال من مرحلة لأخرى (مثلاً من التخطيط للبناء):** شغّل أمر `set-phase`.
- **عند مواجهة خطأ برمجي غامض وإيجاد حل له:** شغّل أمر `add-note issue_resolved` لتوثيق الحل.

## 🔄 دورة حياة الـ Digest
1. **التهيئة:** يُنشأ الملف لأول مرة إما تلقائياً أو عبر أمر `compact`.
2. **التراكم:** يتم إضافة القرارات والملاحظات أثناء المحادثة.
3. **الضغط التلقائي:** السكريبت يضمن ألا يتجاوز الملف 100 سطر بأسلوب FIFO (يحذف أقدم المشاكل المحلولة إذا اقترب من الحد الأقصى)، لضمان بقاء الحجم صغيراً ومقروءاً.
4. **الاستهلاك:** الوكيل يقرأه باستمرار كبوصلة للعمل دون الحاجة لقراءة المحادثة السابقة بأكملها.

# نظام الاستئناف الذكي (Smart Resume)

## 🗂️ الفرق بين الملفات الثلاثة
- `.session_state.json`: **قاعدة البيانات الأساسية**. يحفظ كل تفاصيل الحالة كملف JSON مخصص للمعالجة البرمجية والسكريبتات.
- `session_digest.md`: **الخلاصة للوكيل**. يُولد من الـ JSON ويكون موجهاً للقراءة من قبل الوكيل أثناء عمله لتذكيره بالقرارات (أقل من 100 سطر).
- `resume_brief.md`: **تذكرة الدخول لمحادثة جديدة**. يُولد فقط عند طلب الاستئناف (`resume`)، ويحتوي على برومبت جاهز يتم لصقه لبدء الجلسة الجديدة.

## 🚀 متى تستخدم save و resume؟
- **save**: عندما تريد حفظ الحالة الحالية قسرياً، رغم أنها تُحفظ تلقائياً في كل مرة تقوم فيها بتحديث القرارات أو المرحلة.
- **resume**: عندما تقرر فتح **محادثة جديدة** (New Chat) إما بسبب تعليق الوكيل، أو رغبتك بالعودة للعمل في يوم آخر، وتريد للوكيل أن يتذكر كل ما تم الاتفاق عليه سابقاً بدون أن تبدأ من الصفر.

## ⚙️ سير العمل الكامل للاستئناف (Workflow)
عندما تتعطل المحادثة الحالية وترغب بفتح محادثة جديدة لنفس المشروع:
1. **الحفظ (اختياري):** شغّل `python scripts/session_manager.py save <project_id>` لحفظ آخر التعديلات إذا لزم الأمر.
2. **توليد حزمة الاستئناف:** شغّل `python scripts/session_manager.py resume <project_id>`.
3. **فتح الجلسة الجديدة:** افتح محادثة جديدة تماماً مع الوكيل.
4. **التلقين:** افتح ملف `resume_brief.md` وانسخ "البرومبت الجاهز" الموجود فيه، ثم ألصقه في المحادثة الجديدة كأول رسالة.
5. الوكيل سيقوم بقراءة الملفات الأساسية المذكورة في البرومبت ويستأنف العمل فوراً من المرحلة التي توقف عندها، متذكراً كل القرارات المعتمدة والمرفوضة.

## 📌 أمثلة واقعية للاستخدام

- **حالة 1: العودة للعمل في اليوم التالي**
  عملت على "تخطيط" المشروع `tech_world` اليوم وأغلقت الجهاز. في اليوم التالي، تفتح محادثة جديدة وتطلب من الوكيل استئناف العمل عبر لصق برومبت `resume_brief.md`، ليكمل الوكيل فوراً بناء المشاهد.
  
- **حالة 2: الوكيل بدأ بالهلوسة أو التعليق**
  المحادثة أصبحت ثقيلة جداً وبدأ الوكيل بالخروج عن المسار. كمستخدم، تشغّل أمر الاستئناف `resume`، تفتح محادثة جديدة، وتلصق البرومبت ليحصل على وكيل جديد ونظيف ولكنه يمتلك "الذاكرة" اللازمة لمتابعة العمل دون تخريب السياق.

# نظام القراءة الانتقائية (Selective Reading)

## 🤔 لماذا القراءة الانتقائية مهمة؟
البروتوكول القديم كان يطلب من الوكيل قراءة كافة مراجع المشروع وأدلة التصميم (أكثر من 5 ملفات ضخمة) في **كل خطوة**. هذا يعني أن السياق المتراكم يمتلئ بآلاف الأسطر غير الضرورية للمرحلة الحالية، مما يتسبب في تعليق الوكيل، زيادة استهلاك الرموز، وبطء الاستجابة.

## 📉 كيف يقلل هذا النظام من السياق المتراكم؟
يعتمد النظام على السكريبت `selective_reader.py`، والذي يحدد للوكيل قائمة الملفات المسموح له بقراءتها في كل مرحلة على حدة، مما يؤدي إلى توفير ما بين **60% إلى 90%** من حجم السياق المُهدر. 

## 📌 أمثلة على القراءة لكل مرحلة

- **في مرحلة التخطيط (`plan`):**
  يقرأ الوكيل القوالب ومراجع الذوق الحركي (Motion Taste)، ولكنه **لا يقرأ** أياً من ملفات الأكواد السابقة أو المشاهد.

- **في مرحلة بناء مشهد (`build_scene_3` مثلاً):**
  يقرأ الوكيل خطة المشهد الحالي، الكود السابق `Scene2.tsx` فقط كمرجع، وقوائم القوالب/المؤثرات، ولكنه **لا يقرأ** الدليل الإرشادي الكامل للحركة لأنه قرأه بالفعل في التخطيط.

- **في مرحلة الصوتيات (`audio`):**
  يقرأ الوكيل التوقيتات ومصفوفة المؤثرات الصوتية `SFX_BINDING_MATRIX` فقط، **وليس له حق** في قراءة قوالب الأكواد (React Templates).

## ⚠️ الاستثناءات (متى يمكن خرق القاعدة؟)
لا يحق للوكيل قراءة ملفات خارج المصفوفة المحددة لمرحلته إلا في 3 حالات ضيقة:
1. طلب صريح ومباشر من المستخدم لقراءة ملف معين.
2. ظهور خطأ (Error/Bug) أثناء العمل، يتطلب العودة لملف مرجعي لاكتشاف سبب الخلل.
3. استكشاف أو تشخيص مشكلة في مكون أو قالب React معين.

## 🗂️ تنظيف transcript الدوري

### 🤔 لماذا تنظيف السجل مهم؟
ملف `transcript.jsonl` ينمو بلا حدود مع كل محادثة ويحتوي على سجل كامل للخطوات. مع المشاريع الطويلة، يصبح الملف كبيراً جداً، مما يبطئ استجابة الوكيل ويزيد من تراكم السياق. هذا النظام يضمن بقاء أحدث المحادثات فقط مع أرشفة الباقي لحفظ الخصوصية وتقليل العبء بنسبة تصل لـ 15%.

### ⏱️ متى يحدث التنظيف؟
1. **تلقائياً** عند تشغيل `context_compactor.py compact` إذا كان السجل > 50 جولة.
2. **تلقائياً** عند تشغيل `session_manager.py resume` للاستئناف.
3. **يدوياً** عبر الأمر: `python transcript_cleaner.py clean <session_id>`

### 🧹 ماذا يحدث أثناء التنظيف؟
- **آخر 20 جولة:** تبقى نشطة في ملف `transcript.jsonl`.
- **الجولات الأقدم:** تُنقل وتؤرشف في ملف باسم `transcript_archive_YYYYMMDD_HHMMSS.jsonl`.
- **نسخة احتياطية:** تُنشأ دائماً قبل أي عملية حذف لضمان عدم فقدان البيانات.

### 🔍 استرجاع البيانات المؤرشفة
في حال احتجت للرجوع للمحادثات القديمة، ستجد جميع الملفات المؤرشفة بنفس مجلد السجل الأصلي. يمكنك قراءتها أو استخدام أمر `archive` لأرشفة يدوية دون حذف.

### ⚠️ الاستثناءات والحماية
لا يتم تنظيف السجل في الحالات التالية:
- إذا كان السجل أقل من 30 جولة (لحماية البيانات من الحذف الخاطئ).
- إذا تم التنظيف بالفعل خلال آخر 30 دقيقة (لمنع الإفراط في إنشاء أرشيفات متتالية).
