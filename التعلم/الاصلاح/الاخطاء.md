# 1. State / Orchestration / Recovery

## 1. STATE-001 — يوجد أكثر من Authority لتغيير Lifecycle
**الأولوية: P0 — مثبت في التدقيق وموجود الآن في `main`.**

المشكلة: المفروض `pipeline.py + StateMachine` يكونا authority الرسمية لتقدم المشروع. لكن [`api/services/pipeline_service.py`](https://github.com/m2menqawsh-maker/motion/blob/main/api/services/pipeline_service.py) ما زال يحتوي `finish_stage()` و`approve_gate()` ويغير `state.lifecycle_state` مباشرة.

يعني API يستطيع القول إن المشروع أصبح `BLUEPRINT_READY` أو `REVIEW_APPROVED` بدون إثبات أن gates المطلوبة اشتغلت ونجحت. هذه هي المشكلة التي أثبتها التدقيق كـ`STATE-001`. :chatgpt-content-reference{index="1"}

**الإصلاح الأفضل:** أنشئ `LifecycleService` أو `TransitionService` واحد فقط. لا يسمح لأي Router أو Service بكتابة `lifecycle_state`. كل transition يجب أن يطلب: current revision، target state، mandatory evidence، gate result، actor/reason. الـAPI يطلب action، والـLifecycleService وحده يقرر هل transition قانونية.

**اختبار الإغلاق:** search/architecture test يمنع أي assignment لـ`lifecycle_state` خارج authority واحدة. وتجربة `finish_stage("2")` بدون Blueprint validation يجب أن ترجع 409/422 ولا تغير state.

---

## 2. Gate API يقبل operations غير صحيحة ويرجع Success
**P0 — موجود حاليًا.**

`PipelineService` يعرف mappings محددة، لكن `finish_stage()` إذا أخذ stage غير معروف لا يفشل؛ قد لا يغير state لكنه ما زال يرجع response ناجح. وكذلك `approve_gate()` يستطيع تسجيل `approved_by` حتى إذا كان gate غير معروف.

والـ`VALID_GATES` نفسها موجودة لكن ليست enforcement حقيقية لهذه العمليات.

**الإصلاح:** استخدم enums واضحة في request schema، واحذف stringly-typed `"0"`, `"1"`, `"gate_4"`. أي gate/stage غير معروف = `422 INVALID_STAGE/GATE`.

**اختبار:** unknown stage/gate يجب ألا يكتب أي byte في `.pipeline_state.json`.

---

## 3. `reject_gate()` ليس Rejection حقيقيًا
**P0 للـGUI.**

في [`api/services/gate_service.py`](https://github.com/m2menqawsh-maker/motion/blob/main/api/services/gate_service.py)، `reject_gate()` يستدعي `start_stage()`، ويضيف `note` إلى response فقط. الـnote لا تحفظ كقرار review موثوق، ولا يوجد invalidation صريح للموافقة.

**الإصلاح:** عرّف Review Decision رسميًا:

`PENDING | APPROVED | REJECTED`

مع:

`actor_id`, `decided_at`, `reason`, `blueprint_hash`, `probe_report_hash`, `revision`.

عند Reject: المشروع يبقى/يرجع إلى حالة قابلة للتعديل، الموافقة السابقة تُلغى، وأي downstream evidence يصبح stale.

## 4. CONC-001 — Lost Update / Stale Write
**P0 — مثبت.**

[`StateStore.save()`](https://github.com/m2menqawsh-maker/motion/blob/main/scripts/core/state_store.py) يعمل temp file + fsync + replace. هذا يجعل استبدال الملف atomic نسبيًا، لكنه لا يحمي من Writer آخر قرأ revision قديمة.

الـ`asyncio.Lock` الموجود في API process-local فقط. التدقيق أثبت stale overwrite/revision regression. :chatgpt-content-reference{index="2"}

وفوق ذلك، كل writers يستخدمون نفس temp filename `.pipeline_state.json.tmp`.

**الإصلاح:** اختر حسب deployment:

إذا التطبيق single-host/single-user: single writer process + OS file lock + CAS على revision.

إذا سيكون multiworker/server: أنقل state إلى PostgreSQL أو SQLite/WAL حسب architecture، واستخدم optimistic locking:

`UPDATE ... WHERE project_id=? AND revision=?`

ثم increment revision transactionally.

**الإغلاق:** اختبار Process A وProcess B يقرآن revision=10؛ واحد فقط يسمح له كتابة revision=11، والثاني يحصل `StateConflict`.

---

## 5. STATE-002 — Lifecycle + Evidence + Revision ليست Transaction واحدة
**P0.**

`pipeline.py` يبني records، يعدل lifecycle، ثم يحفظ. Routes أخرى تغير lifecycle مباشرة. `mark_failed()` يكتب state بطريقة أخرى.

الدليل أثبت أن `lifecycle_state`, `artifact_records`, `revision`, `updated_at` لا تخضع لنفس authority. هذا أصل معماري وليس bug منفرد.

**الإصلاح:** `transition()` يجب أن يكون transaction كاملة:

`validate preconditions → validate mandatory evidence → mutate state → append transition history → increment revision → persist atomically`.

ممنوع `state.lifecycle_state = ...` خارجها.

---

## 6. Corrupted state يُعامل كأنه لا يوجد State
**P0.**

[`StateStore.load()`](https://github.com/m2menqawsh-maker/motion/blob/main/scripts/core/state_store.py) يمسك `Exception` كلها ويرجع `None`.

هذا يساوي:

missing state = corrupt JSON = invalid schema = filesystem error.

**الإصلاح:** ثلاث نتائج منفصلة:

`StateNotFound`  
`StateCorrupted`  
`StateIOError`

والـcorruption يجب أن يوقف lifecycle fail-closed، لا يبدأ مشروعًا جديدًا.

---

## 7. REC-001 — Recovery يفحص الموجود بدل المطلوب
**P0.**

التدقيق أثبت مثالًا خطيرًا: `COMPLETE + artifact_records=[] + out.mp4 missing` يمكن أن يعتبر resumable. :chatgpt-content-reference{index="3"}

الكود الحالي ما زال يفعل ذلك في [`recovery_engine.py`](https://github.com/m2menqawsh-maker/motion/blob/main/scripts/core/recovery_engine.py): loop فقط على `state.artifact_records`.

**الإصلاح:** عرف `REQUIRED_EVIDENCE_BY_STATE`.

مثلاً COMPLETE لا تثق بها إلا إذا كانت سلسلة evidence المطلوبة سليمة، وليس فقط records الموجودة.

---

## 8. Evidence تختفي أثناء تقدم المشروع
**P0.**

في `pipeline.py`:

`state.artifact_records = refs`

أي كل transition تستبدل evidence السابقة. والأسوأ:

`AWAITING_REVIEW -> []`  
`REVIEW_APPROVED -> []`  
`COMPLETE -> []`

**الإصلاح:** لا تجعل Evidence snapshot واحدًا قابلًا للمسح. استخدم append-only artifact/evidence ledger أو state snapshot يحتوي chain كاملة. الـState الحالية تشير إلى evidence IDs، ولا تمسح تاريخها.

---

## 9. Recovery يستطيع اكتشاف مشكلة لكنه لا ينفذ Rollback صالحًا
**P0.**

الدليل أثبت scenario: Recovery يكتشف hash mismatch، pipeline يبدأ من DRAFT، لكن persisted state ما زالت advanced، فيصطدم transition التالي.

**الإصلاح:** recovery لا ترجع مجرد `next_state`. يجب أن تنتج `RecoveryPlan` رسميًا:

`last_valid_state`  
`invalidated_artifacts`  
`stages_to_replay`  
`reason`

ثم authority تنفذ rollback/reconciliation transaction قبل إعادة التشغيل.

---

## 10. `FAILED` semantics غير متماسكة
**P1.**

StateMachine تسمح نظريًا recovery من FAILED، لكن `pipeline.py` عند رؤيتها يخرج مباشرة. `mark_failed()` كذلك يتجاوز transition المعتاد.

**الإصلاح:** اختر contract واحد:

FAILED إما terminal ويحتاج explicit `retry/recover` action، أو recoverable وله RecoveryPlan.

لا تترك الاثنين معًا.

# 2. Failure / Retry / Error Model

## 11. كل الأخطاء تقريبًا تتحول إلى `GATE_EXECUTION_FAILED`
**P1 — مثبت.**

`run_script()` في [`pipeline.py`](https://github.com/m2menqawsh-maker/motion/blob/main/scripts/pipeline.py) ما زال يحول Exceptions إلى `FailureCode.GATE_EXECUTION_FAILED` رغم أن [`failure_model.py`](https://github.com/m2menqawsh-maker/motion/blob/main/scripts/core/failure_model.py) يحتوي taxonomy ممتازة أصلاً.

التدقيق وثق هذا الخلل. :chatgpt-content-reference{index="4"}

**الإصلاح:** كل gate يعيد structured machine-readable result/error:

`BLUEPRINT_VALIDATION_FAILED`, `TEMPLATE_VALIDATION_FAILED`, `RENDER_TIMEOUT`...

ولا تعتمد على exit code وحده لتخمين الخطأ.

---

## 12. Retry يعيد أخطاء Deterministic
**P1.**

بسبب المشكلة السابقة، invalid Blueprint قد يعامل كـinternal retryable error.

**الإصلاح:** classification أولًا، Retry ثانيًا.

Validation reject = لا retry.  
Network/transient/timeout = retry.  
Render crash = conditional retry.  
Security violation = never retry.

---

## 13. `CONDITIONALLY_RETRYABLE` لا يحصل على Runtime validity الحقيقي
**P1.**

`RetryPolicyEngine.evaluate()` لديه `is_state_valid`, لكن `pipeline.py` لا يمرر check حقيقي؛ يستخدم default `True`.

**الإصلاح:** قبل retry تحقق من input hashes، current state revision، partial side effects، lock ownership، idempotency token.

---

## 14. Structured error history ليست موثوقة
**P1.**

لديك `structured_errors` في `ProjectState`، لكن failure path الرئيسي لا يضمن append لها.

**الإصلاح:** كل Failure terminal أو retry event يسجل structured error/event في persistent event log.

للـGUI هذا ضروري حتى تعرض للمستخدم “ليش فشل؟” بدل stdout خام.

# 3. Approval / Human Trust / Security

## 15. Approval identity self-asserted
**P0.**

[`POST /gates/.../approve`](https://github.com/m2menqawsh-maker/motion/blob/main/api/routers/gates.py) ما زال يقبل:

`by: str = "gui"`

ثم يحفظه كـ`approved_by`.

الدليل يثبت أن `approved_by value != verified identity`. :chatgpt-content-reference{index="5"}

**الإصلاح:** لا تقبل `approved_by` من body/query. خذه من authenticated principal.

Local-only app: trusted local session/OS identity.

Server: OIDC/OAuth/JWT session + RBAC.

---

## 16. لا يوجد Application-Level Authentication/Authorization
**P0 إذا الـGUI سيصبح network-accessible.**

[`api/main.py`](https://github.com/m2menqawsh-maker/motion/blob/main/api/main.py) يركب routers مباشرة ولا يوجد dependency/auth middleware. وهذا يتطابق مع Full Discovery.

هذا لا يعني أن API مكشوفة للإنترنت حاليًا؛ لكنه يعني أن repository نفسه لا يوفر boundary auth.

**الإصلاح:** قبل GUI production، عرّف principal وroles:

`viewer`, `editor`, `reviewer`, `operator/admin`.

Approval تحديدًا يحتاج permission منفصلة.

---

## 17. Managed Render يتجاوز Marker بدون إثبات البديل
**P0.**

[`render_project.py`](https://github.com/m2menqawsh-maker/motion/blob/main/scripts/render_project.py):

إذا `AGY_IS_MANAGED=1`، عدم وجود `.studio_approved` لا يمنع render.

لكن السكربت نفسه لا يثبت أن state الحالية `REVIEW_APPROVED` وأن approval_metadata سليمة وحديثة.

**الإصلاح:** `render_project` نفسه يجب أن ينفذ `assert_render_authorized(project_id, current_hashes)`، بغض النظر عن من استدعاه.

## 18. Approval غير مربوطة بالنسخة التي تمت مراجعتها
**P0.**

التدقيق: الإنسان يستطيع الموافقة على A، يتغير Blueprint إلى B، وتبقى metadata. :chatgpt-content-reference{index="6"}

`open_studio.py` يستخدم mtime فقط؛ هذا ليس binding للموافقة.

**الإصلاح:** approval record يحمل:

`blueprint_sha256`  
`master_plan_sha256`  
`media_map_sha256`  
`probe_report_sha256`  
`review_revision`

أي تغير بعدها يبطل approval تلقائيًا.

## 19. تعديل Blueprint/Brand/Overrides لا يعمل Downstream Invalidation
**P0 للـGUI.**

[`blueprint.py`](https://github.com/m2menqawsh-maker/motion/blob/main/api/routers/blueprint.py) يكتب الملف مباشرة. لا يوجد transition/invalidation للـProbe أو approval أو render.

**الإصلاح:** كل Artifact mutation تمر بـArtifactService يعرف dependencies.

مثلاً تغيير Blueprint بعد approval:

`REVIEW_APPROVED → invalidated → BLUEPRINT_READY/MATERIALIZED` بحسب نوع التغيير.

ولا يُسمح بكتابة artifact تحت state متقدمة بدون invalidation صريح.

## 20. ASSET-009 — Path traversal في Materializer
**P0 أمني.**

[`materialize_project.py`](https://github.com/m2menqawsh-maker/motion/blob/main/scripts/generators/materialize_project.py) ما زال يستخدم:

`absolute path -> return as-is`

و:

`pub_media / f"{asset_id}{suffix}"`

بدون `safe_resolve()`.

التدقيق أثبت absolute external source و`../../../../../sentinel`. :chatgpt-content-reference{index="7"}

**الإصلاح:** كل source/destination عبر `safe_resolve`. Reject absolute paths، `..`, symlink escape. الـasset ID لا يُستخدم raw في path؛ validate canonical regex أولًا.

**اختبارات:** Unix traversal، Windows drive، backslashes، encoded traversal، symlink escape، malicious asset ID.

## 21. `safe_subprocess` Docker allowlist فيها ثغرة Policy
**P1 — وجدتها مباشرة في `main`.**

[`security.py`](https://github.com/m2menqawsh-maker/motion/blob/main/scripts/security/security.py) يحاول السماح بـ`docker info` و`docker run`، لكن branch:

`elif cmd == "docker": pass`

يجعل Docker subcommands غير المدرجة تمر عند فشل allowlist.

**الإصلاح:** command policy parser حقيقي. بالنسبة لـDocker، whitelist subcommand + allowed flags، ولا يوجد generic `pass`.

## 22. `SKIP_STRICT_QC` يستطيع تحويل Hard Failure إلى Success
**P0 production trust boundary.**

## 23. ASSET-001 — Manifest Contract منقسم
**P0.**

`asset_id=ast_*`,  
`source=incoming|cache|ready`.

`kind`

`status` = incoming/processing/ready  
`source_path`  
`processed_path`  
`content_hash`  
`processing_spec_hash`  
`metadata`

افصل provenance عن storage status؛ حاليًا يتم خلط مفهومين.

## 28. ASSET-003 — Materialization غير Atomic
**P0.**

Materializer ينسخ الملفات واحدًا واحدًا ثم يكتب `media_map.json` ثم يفحص `fails`.

**الإصلاح:** staging transaction:

`validate all → copy all to staging dir → build map → fsync → atomic directory/map publish`.

أي failure قبل commit يمسح staging بالكامل.

# 10. مشاكل Architecture أعمق من أي Bug منفرد

هذه هي الجذور التي لو لم تصلحها ستعود المشاكل بأسماء أخرى.

## 88. Source of Truth Fragmentation
**P0 root cause.**

لديك أكثر من authority لنفس الحقيقة:

State: Pipeline / API  
Template: Index / filename / registry  
Assets: Manifest schema / gate / Blueprint / materializer  
Approval: marker / state metadata  
Audio: project / Blueprint examples / runtime.

**الإصلاح:** اكتب `Contract Authority Matrix` رسميًا: لكل domain authority واحدة، والباقي generated/adapters.

---

## 89. “File exists” كثيرًا ما يُخلط مع “Invariant enforced”
**P1 root cause.**

هذا pattern موجود في schemas, tools, QC functions, references, reports.

**الإصلاح:** لكل invariant حدد `Enforcer + point of execution + failure behavior + regression test`.

---

## 90. Artifact mutation ليست Dependency-aware
**P0 root cause للـGUI.**

تغيير Blueprint لا يخبر Probe/Approval/Render أن evidence أصبحت stale.

**الإصلاح:** Artifact Dependency Graph executable، وليس Documentation فقط.

مثلاً:

`Blueprint → Materialization → Probe → Review → Render → Final QC`.

أي تعديل upstream ي invalidates downstream.

---

## 91. Filesystem Truth وLifecycle Truth منفصلان
**P0.**

أوضح مثال materialization partial writes.

**الإصلاح:** transaction/staging patterns + state commit بعد artifact commit فقط.

---

## 92. Agent workflow وGUI workflow ليسا نفس Product Surface
**P1 قبل GUI.**

Agent يستطيع MCP/tools/filesystem، بينما API GUI لا يملك نفس capabilities.

**الإصلاح:** لا تجعل GUI تقلد Agent filesystem actions. اجعل الاثنين يستهلكان نفس Domain Services:

AssetService  
ProjectService  
ArtifactService  
PipelineService  
ReviewService.

الـAgent يمكن أن يكون client آخر لهذه الخدمات لاحقًا.

# 11. نقاط ما زالت Deferred/Unknown ولا يجوز إعلانها Bugs نهائية بدون إعادة Verification

من القراءة الكاملة للملف توجد أيضًا عناصر يجب حسمها أثناء remediation، لكن لا أنصح بإدخالها كـ“confirmed defect” قبل reproduction:

هذه تدخل Cleanup/Reconciliation cluster، وليس P0 fixes عشوائية.

# الترتيب الذي أنصحك تنفذ فيه الإصلاح

لا تصلح الـ92 نقطة واحدة واحدة. معظمها أعراض لـ6–8 جذور.

**Cluster 0 — Baseline/Reconciliation.** لا تبدأ بإصلاح مباشر على `main` أو `remediation/master-plan`. حافظ على `1db091b` كـimmutable evidence baseline. أنشئ implementation/reconciliation branch من current `main @ 4b96960`، وانقل إليها reproductions الخاصة بكل finding. كل Finding يأخذ `CONFIRMED_ON_MAIN / CHANGED / CANNOT_REPRODUCE`. السبب أن `main` وaudit branch diverged حاليًا.

**Cluster 1 — Security & Trust Boundaries.** ASSET-009، auth، approval identity/hash binding، `SKIP_STRICT_QC`، subprocess policy. هذه قبل أي refactor واسع.

**Cluster 2 — State Authority / Recovery / Concurrency.** LifecycleService واحد، state transaction، revision/CAS، required evidence matrix، real recovery plans، error persistence.

**Cluster 3 — Canonical Contracts.** Manifest v2، project identity، asset types/IDs، Blueprint, audio، template identity. هنا أيضًا migration/version strategy. لا تبدأ media rewrite قبل حسم contracts.

**Cluster 4 — Materialization & Resolution.** Transactional materializer، canonical resolver، cache identity، stale cleanup، status transitions، fail-closed refs.

**Cluster 5 — Template Runtime.** Registry واحدة authority، validator/materializer يستخدمانها، template-specific schemas، effects/transitions، full render parser.

**Cluster 6 — Render/QC.** Unified render payload، Probe canonical timing، strict Final QC، AV sync policy، no production bypasses، Docker parity، reproducible environment.

**Cluster 7 — API Foundation قبل GUI.** هنا فقط أبني backend الذي تستحق الـGUI الاعتماد عليه: canonical REST models، auth، project/artifact/asset/review/run services، persistent jobs، cancellation، live events، output serving، optimistic concurrency.

**Cluster 8 — CI/Governance/Operations.** protected main، fixed hooks، dependency locks، Docker CI، strict E2E، recovery/concurrency/security tests، logs/metrics/readiness.

بعدها Final Architecture Re-Audit.

# Production Readiness Gate النهائي

قبل أن تقول “Clean backend، نبدأ GUI”، يجب أن يتحقق التالي كله:

1. صفر P0 مفتوحة وصفر P1 غير مقبولة صراحة.
2. كل Finding مثبت قديم لديه reproduction كانت تفشل ثم أصبحت تمر.
3. لا يوجد direct lifecycle mutation خارج Lifecycle Authority.
4. كل canonical artifact يمر بنفس contract في Python وTypeScript.
5. traversal/unknown refs/duplicate IDs/stale assets كلها fail closed.
6. approval مربوطة cryptographically/revision-wise بالنسخة التي راجعها الإنسان.
7. recovery ينجح بعد kill/restart من كل stage الحرجة.
8. concurrent writers لا يستطيعان خسارة update.
9. Local وDocker ينتجان نفس render contract ونفس نتائج القبول.
10. E2E تعمل بدون `SKIP_STRICT_QC`.
11. E2E تشمل 9:16 و16:9 و1:1، وعدة template families، audio/media، approval، restart.
12. negative security tests كلها خضراء.
13. API auth/authorization موجودة إذا deployment شبكي.
14. background jobs durable وقابلة للاستئناف/الإلغاء.
15. GUI تستطيع رفع media وقراءة reports والوصول للفيديو بدون filesystem hacks.
16. dependencies locked؛ لا runtime `pip install`.
17. CI تشمل Python + TS + contract generation + Docker + strict E2E + security gates.
18. `main` protected وrequired checks mandatory.
19. readiness/metrics/logging والbackup/storage policy محددة ومختبرة.
20. Final Architecture Re-Audit لا يعيد فتح أي root cause.

إذا أغلقت هذه القائمة فعلاً، وقتها المشروع ليس فقط “التستات خضراء”؛ يصبح عنده **trust chain حقيقية من User/Agent/API → Artifacts → State → Materialization → Review → Render → QC**. وهذا هو الأساس الصحيح لتبدأ فوقه GUI بدل أن تضيف طبقة جديدة فوق مشاكل قديمة.

أقوى خطوة تالية الآن ليست كتابة كود. هي أن نحوّل هذا التقرير إلى **Master Remediation Ledger تنفيذي**: كل ID أعلاه → الملفات التي ستتغير → dependencies → الاختبار الذي يجب أن يفشل قبل الإصلاح → patch المطلوب → acceptance criteria → ترتيب الـcommits. وقتها سيكون عندك roadmap يمكن تنفيذها commit-by-commit بدون الضياع.
