**تاريخ الخطة:** 26 سبتمبر 2026

**مدخل التنفيذ:** [Master Remediation Ledger](Master_Remediation_Ledger_motion.xlsx)، 92 بندًا، 27 حزمة أصلية `S00–S26`، مع إضافة حزمة تنفيذية خارج التسلسل الأصلي `S24.5 — Multi-Tenant SaaS Foundation`.  
**مرجع الأدلة التاريخي:** `remediation/master-plan @ 1db091b420432dd2a6eb612596d76f0f3d2ef209` كما ورد في «دليل المشروع كامل - جاهز للإصلاح(2).pdf»، و«المنهجية(2).md».

## 1. النتيجة التي نسعى إليها

يستقبل النظام مشروعًا وأصولًا عبر واجهة موثقة، يتحقق من عقد كل artifact، يمرره عبر انتقالات حالة لا يمكن تجاوزها، ينشر الأصول بصورة متسقة، يعرض معاينة قابلة للمراجعة، يربط موافقة إنسان بنسخة محددة، يرندر الفيديو في بيئة قابلة لإعادة البناء، ثم يثبت Final QC على الفيديو نفسه. يمكن إيقاف العامل أو إعادة تشغيله أو تعديل مشروع من تبويبين دون فقدان تحديث أو منح نجاح كاذب. تستطيع GUI إدارة المشروع والميديا والتقارير والفيديو من API موحدة.

هذا هو تعريف الإنجاز؛ عدد الاختبارات الخضراء أو وجود ملفات schema وحدهما لا يحققانه.


### حالة التنفيذ الحالية بعد S24.5

تمت إضافة أساس SaaS متعدد المستأجرين بعد `S24`: هوية `User → Workspace → WorkspaceMember → Project`، `workspace_id` إلزامية لكل مشروع، PostgreSQL هو هدف persistence الإنتاجي، `StorageService` تفصل التخزين المحلي عن S3-compatible storage، والـworkers تستخدم مساحات تنفيذ مؤقتة بدل اعتماد القرص المحلي كمصدر حقيقة دائم. تم كذلك إدخال `TenantContext` وRBAC وعزل المستأجرين وCAS على الحالة والوظائف.

هذه الإضافة **ليست SaaS تجاريًا كاملًا** بعد؛ لا تشمل Billing أو Product Auth UX أو AI subsystem أو GUI النهائي. وهي لا تغلق أي Finding تاريخية تلقائيًا دون إعادة التحقق في `S25`.

**الموضع الحالي في التسلسل:** `S24 ✅ → S24.5 ✅ → S25 ← التالي → S26`.

### الهدف التشغيلي المعتمد بعد S24.5

الهدف التشغيلي أصبح **Multi-user SaaS** بدل افتراض single-host المحلي. القرار المعتمد هو: FastAPI مع `TenantContext`، PostgreSQL للحالة والوظائف والمعاملات، `StorageService` بواجهة موحدة مع `LocalStorageBackend` للتطوير و`S3CompatibleStorageBackend` للإنتاج، وworkers منفصلة تستخدم مساحة تنفيذ مؤقتة ثم ترفع المخرجات إلى التخزين الدائم.

الهوية التنظيمية هي `User → Workspace → WorkspaceMember → Project`، وكل Project يجب أن تنتمي إلى Workspace واحدة دون legacy nulls. لا تُستخدم مشاريع التطوير الحالية كبيانات production ولا يلزم migration تاريخية لها؛ المطلوب فقط schema migrations idempotent واختبارات إعادة البناء.

### قواعد تحكم الخطة

1. **لكل بند:** تأكيده على `main` الحالي → اختبار أحمر قابل للتكرار → patch → اختبار أخضر → CI → PR/commit SHA في السجل. حالات `CHANGED` و`CANNOT_REPRODUCE` تحتاج دليلًا، لا تُحسب إصلاحًا.
2. **لكل عقد:** authority واحدة، نسخة عقد محددة، هجرة للأمثلة والبيانات القديمة، واختبارات قبول من Python وTypeScript معًا.
3. **لكل artifact منشور:** محتوى وبصمة ونسخة ومالك وسلسلة اعتماد؛ تغير upstream يبطل الأدلة downstream.
4. **لكل انتقال حالة:** دليل مطلوب، actor مصرح، معاملة، revision متزايد، وسلوك معلوم عند التعارض والانقطاع.
5. **لكل حزمة دمج:** نطاق صغير، اختبارات سلبية وسعيدة، خطة ترحيل/تراجع عند تغيير البيانات، ولا تجاوزات QC إنتاجية.

[وثائق GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository).

### المرحلة 0 — إثبات الواقع وتجهيز تنفيذ لا يضيع الأدلة (`S00`)

**العمل:**

- ثبّت audit baseline الأصلي للقراءة فقط، وسجّل SHA حقيقيًا لـ`main` وقت الانطلاق. اعمل في branch إصلاح من `main`، لا في `main` أو فرع الأدلة.
- جرد 92 بندًا: `CONFIRMED_ON_MAIN` / `CHANGED` / `CANNOT_REPRODUCE` / `ENVIRONMENT_BLOCKED`، مع أمر إعادة الإنتاج، النتيجة الفعلية، الملف، وSHA. صحح ترقيم أول 21 بندًا تحريريًا مقابل النص الأصلي إن توفر.
- شغّل CI الحالية مرة نظيفة وسجل النتائج، مسارات CLI/API/Local/Docker المتاحة، وبيانات fixture التي تحتاج migration.
- حدد نمط النشر وحجم البيانات، مستودع state/jobs، هوية المستخدم، سياسة backward compatibility، ومن يملك قرار استثناء P1.
- فعّل ruleset أولية: PR مطلوب، منع force push وdirect push، ومراجعة؛ أضف الفحوص المطلوبة المتوفرة بثبات، ثم حدّثها بعد اكتمال CI.

**اختبارات الخروج:** reproductions لعيوب P0 الحرجة قابلة للتكرار على بيئة معزولة أو لها تعليل `CHANGED` محدد؛ قرار معماري مكتوب؛ نسخة ledger محدثة. إذا كان `main` قد أصلح بندًا، لا تنقل patch قديمًا دون اختبار regression.

### المرحلة 1 — سد حدود الثقة التي تسمح بنتائج كاذبة (`S01–S02`)

**النطاق:** `ASSET-009`، هوية ومصادقة API، انتحال `approved_by`، سياسة subprocess، و`SKIP_STRICT_QC`؛ لا تنتظر اكتمال إعادة تصميم Manifest لحجب traversal.

**التنفيذ:**

1. path confinement لمصدر الأصل والهدف بعد canonical resolution، مع فحص ID، symlink escape، absolute path، أسماء ملفات خطرة، وعدم ترك side effects عند الرفض.
2. principal خادم موثوقة وauthorization على كل project/asset/review/run/output؛ لا تقبل أسماء الموافقين من query/body. رفض الوصول للمشروع الآخر حتى لو ID صحيح.
3. parser للأوامر المسموحة مع subcommands/flags محددة، خاصة Docker، وspawn دون shell interpolation عند الإمكان.
4. إزالة ambient `SKIP_STRICT_QC` من مسار الإنتاج. إن بقي اختبار قديم، استخدم policy محقونة في اختبار منفصل وتفشل صراحة في `AGY_ENV=production`.
5. واجهة رفع الأصول المستقبلية تُصمم من الآن بـallowlist للنوع والحجم، اسم تخزين يولده الخادم، وإذن للمستخدم؛ OWASP يوصي بطبقات تحقق للرفع والتفويض بدل الثقة في اسم الملف أو `Content-Type` وحده. [مرجع OWASP](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

**اختبارات الخروج:** traversal بالمصدر/ID والروابط الرمزية، أمر Docker غير مسموح، موافقة باسم غير موثق، وصول غير مصرح، وQC hard fail مع env bypass كلها مرفوضة قبل كتابة أثر إنتاجي. أي HTTP 200 سابق غير صحيح يتحول إلى خطأ موثق.

### المرحلة 2 — بناء سلطة موحدة للحالة والدليل (`S03–S09`)

**التسلسل الداخلي:**

1. `S03–S04`: اجعل `LifecycleService.transition()` الطريق الوحيد لتغيير lifecycle. endpoints السابقة إما تشغّل gate حقيقية أو تُزال/تُعلَّم انتقالية؛ لا `finish_stage` أو `approve_gate` يرفع الحالة مباشرة.
2. `S05`: transaction واحدة تغيّر lifecycle وrevision وtimestamp وartifact records وحدث التدقيق. CAS يرفض الكاتب القديم، والقفل/lease يعمل بين العمليات وCLI/API، لا `asyncio.Lock` فقط.
3. `S06`: `RequiredEvidence[state]` إلزامية ومستمرة؛ لا يكفي المرور على قائمة artifact_records الموجودة. سجّل hashes وgeneration IDs لكل مرحلة، ولا تُمحى أدلة المراجعة عند `AWAITING_REVIEW`.
4. `S07`: فرّق `missing state` من `corrupt state`، ثم طبق rollback أو إعادة التحقق من آخر حالة سليمة فعلًا، مع journal لمراحل النشر التي تقطعها الأعطال.
5. `S08`: taxonomy للأخطاء؛ validation rejection حتمي لا يعاد، عطل مؤقت يملك حد retry، و`FAILED` قابلة لاستئناف محدد أو قرار بشري. خزّن structured errors بعد restart.
6. `S09`: `ReviewService` تربط principal وبصمات Blueprint/Manifest/media/probe/contact sheet بـ`review_bundle_id`. `REVIEW_APPROVED` تتطلب `AWAITING_REVIEW` وbundle غير متقادمة. render يتحقق من record واحدة في CLI/API؛ تغير upstream يلغيها.

**اختبارات الخروج:** عمليتان على revision واحد تنتجان نجاحًا وconflict واحدًا دون lost update؛ `COMPLETE` بلا فيديو تفشل؛ state تالفة لا تصبح `DRAFT` تلقائيًا؛ kill/restart بعد كل state حرجة يستأنف من نقطة صالحة؛ رفض stale approval يوقف render. `test_pipeline_integration.py` يعاد بناؤه حتى لا يحمي bypass قديمًا.

### المرحلة 3 — حسم العقود قبل تغيير التخزين والRuntime (`S10–S12`)

**العقود المطلوبة:**

| المجال | السلطة المقترحة | المخرجات المرتبطة |
|---|---|---|
| Manifest | `Manifest v2` + `load_manifest()` | schema، semantic checks، IDs، provenance/status، migration |
| Blueprint | نسخة canonical وتحويل JSON schema/TS/Python متطابق | scene timings، media refs، transitions، effects، aspect/fps |
| Asset identity | ID فريد و`AssetKind` موحد | index، gate، cache، materializer |
| Audio | `AudioPlan` واحد | voiceover/music/volume logical refs ثم runtime paths |
| Project identity | invariant عابر للآثار | directory/state/project/manifest/blueprint IDs |
| Template | Runtime Registry → machine readable generated contract | canonical IDs، aliases، component status |
| Dependency graph | `ArtifactService` | invalidation: Blueprint → materialization → probe → review → render → QC |

**التنفيذ:** اعتمد نسخة عقد وأداة توليد أو اختبارات cross-language من نفس fixtures؛ اشترط canonical parser في كل consumer. جهز migration idempotent، تقرير dry run، نسخة احتياطية، وإمكانية قراءة النسخة القديمة خلال نافذة الانتقال. لا تعيد كتابة media materializer قبل تثبيت مدلول `source/status/kind`.

**اختبارات الخروج:** عينات صالحة وفاسدة تعطي القرار نفسه في Python وTypeScript؛ duplicate IDs وproject mismatch تفشل قبل I/O؛ مشروع قديم يُهاجر ثم يعاد تشغيل migration دون تغيير ثانٍ؛ تغيير Blueprint يبطل أدلة downstream المقصودة.

### المرحلة 4 — نشر الأصول وحلها دون حالة جزئية (`S13–S14`)

**العمل:**

- فحص كل المسارات والأصول والمراجع أولًا؛ إعداد محتوى جديد في staging بجوار مكان النشر وعلى filesystem نفسه؛ fsync بحسب سياسة المتانة؛ نشر generation/map مرجعيًا ثم تنظيف القديم بعد النجاح.
- لأن ملفات الوسائط وقاعدة الحالة لا تشتركان في معاملة واحدة، سجّل `generation_id` أو journal لإعادة المصالحة بعد crash بين نشر artifact وتحديث state؛ لا تعتبر `rename` وحده معاملة موزعة.
- status movement بفحص `expected_status`، وcache key على content hash + normalized processing spec hash + processor version.
- `AssetRef` صريحة لكل حقول media والصوت، وliteral URL/path إن دعمها النظام نوع مختلف بسياسة محددة. `media_map` إلزامية بعد `MATERIALIZED`؛ المجهول يفشل قبل mount.

**اختبارات الخروج:** أصل مفقود مع أصل صحيح لا يغير النسخة العامة؛ حذف أصل يزيل stale file؛ تغير processing spec لا يعيد cache قديمة؛ انقطاع في كل نقطة نشر يعود إما إلى generation القديمة أو الجديدة المعلومة؛ unknown reference لا تصبح raw string في runtime.

### المرحلة 5 — توحيد هوية القالب ومدخل Runtime (`S15–S16`)

**العمل:** generate `template-runtime-contract.json` من registry؛ validator وmaterializer يحلان canonical والaliases عبره؛ enforce regex ID عند البناء؛ إزالة اعتماد validator على `TEMPLATE_INDEX.md` واعتماد materializer على اسم `.tsx`. `parseRenderInput()` على `Root.tsx` قبل merge، مع schemas حقيقية لـcontent/props/surface/effects/transitions لكل عائلة قالب، وقرار حذف feature غير مدعومة بدل ترك طريق ميت.

**اختبارات الخروج:** matrix تضم canonical ID وalias واسم ground truth ممثلًا لكل عائلة؛ الأسماء غير المعروفة والmetadata مثل `Text` ترفض؛ transitions/effects المدعومة تظهر في frames؛ no-op غير معروف يفشل validation.

### المرحلة 6 — نفس عقد الرندر وQC صارمة في كل بيئة (`S17–S20`)

**العمل:**

1. `build_render_input(project_id)` واحدة لـLocal/Studio/Docker/Probe، وحمل mandatory artifacts دون `{}` افتراضية.
2. Probe يشتق frames من `scenes/startFrame/durationFrames` و`fps` العلوي: بداية/منتصف/نهاية كل مشهد، حدود transition ولقطات حركة حرجة. contact sheet والـbundle قابلان للتدقيق قبل فتح المراجعة.
3. Final QC يشتق duration من نهاية المشاهد وaspect من العقد، ينفذ AV sync إذا معتمد، ويفصل `CHECK_FAILED_TO_EXECUTE` عن مخالفة الفيديو. لا تثبيت pip أثناء runtime.
4. Docker image تملك dependencies والرموز والخطوط والنسخ؛ تشغيل non-root مع مشروع mounted منفصل، واختبار parity للمدخلات والنتائج.

**اختبارات الخروج:** 9:16 و16:9 و1:1 مع media/audio وtemplates متنوعة، خطأ black-frame/LUFS analyzer، ملف report ناقص، فشل contact sheet، وفشل QC صريح؛ Local/Docker يستقبلان نفس payload ويعطيان نفس حكم القبول. اجعل أي اختلاف بصري مفهومًا ومقاسًا إن كانت البيئة تنتج bytes مختلفة.

### المرحلة 7 — Backend صالح لتغذية GUI (`S21–S22`)

**عقد API المقصود:** `Project`, `Asset`, `Artifact/Blueprint`, `Run/Job`, `Review/Approval`, `LifecycleState DTO`, `Events`, `Output/QC`، مع نسخة API وهجرة للعملاء السابقين. Router للنقل، Service للقواعد، Repository للتخزين.

**التنفيذ:**

- `POST /projects/{id}/runs` يرجع `run_id` وسجل job محفوظ قبل 202؛ عامل منفصل يلتقط jobs مع lease/heartbeat، ويحفظ stage/events والنتيجة، ويدعم idempotency key وcancel_requested واسترداد orphan jobs. توضح وثائق FastAPI أن `BackgroundTasks` مناسبة للأعمال الصغيرة داخل التطبيق، وتوصي بآليات صف وعمال منفصلين للعمل الثقيل متعدد العمليات؛ لذلك لا نعتمدها كضمان متانة الرندر. [وثائق FastAPI](https://fastapi.tiangolo.com/tutorial/background-tasks/).
- بث أحداث حي من سجل دائم عبر SSE/WebSocket؛ reconnect يستخدم cursor، ولا يعتمد على stdout بعد انتهاء العملية.
- CRUD أصول مع حدود رفع وتفويض، schema للBrand/Overrides، writes ذرية مع `If-Match`/revision و`409 Conflict`، وتقارير/فيديو بتنزيل مفوض وRange requests.
- `GET /health/live` و`/health/ready` بحالة storage/state/worker/FFmpeg/Remotion وفق الهدف التشغيلي؛ ترجع readiness غير جاهزة عند تعطل شرط إلزامي.

**اختبارات الخروج:** عميل API جديد ينشئ مشروعًا ويرفع media ويحرر Blueprint ويتلقى 409 عند التعارض ويشغّل job ويتابع events بعد reconnect ويوافق بعد مراجعة ثم يحمل الفيديو والتقرير. قتل API والعامل أثناء التنفيذ لا يضيع job ولا يترك subprocess حرًا.

### المرحلة 7.5 — أساس SaaS متعدد المستأجرين (`S24.5`) — مكتملة

**الهدف الذي أُنجز:** تحويل الـbackend من افتراض local/single-user إلى أساس multi-tenant دون بناء SaaS التجاري كاملًا.

**المخرجات المعتمدة:**

- `User → Workspace → WorkspaceMember → Project`، و`workspace_id` إلزامية لكل مشروع.
- PostgreSQL هو هدف persistence الإنتاجي للحالة والوظائف، مع CAS وleases؛ SQLite يبقى للتطوير/الاختبار المتوافق.
- `StorageService` موحدة مع Local وS3-compatible backends، ومفاتيح تخزين يولدها الخادم.
- `TenantContext` وRBAC وعزل صارم للمشاريع/assets/runs/reviews/outputs.
- worker workspace مؤقتة؛ المخرجات الدائمة في StorageService.
- usage metering أولي بدون Billing.
- readiness عميقة لقاعدة البيانات والتخزين.
- اختبارات architecture guards وmulti-tenant E2E.

**حدود الحزمة:** لا Billing، لا GUI نهائي، لا AI subsystem، لا Local Media desktop، ولا migration تاريخية للمشاريع التجريبية.

**مهم لـS25:** لا تعتبر نجاح S24.5 إغلاقًا تلقائيًا لأي Finding تاريخية؛ أعد تشغيل reproductions وتصنيف البنود المتأثرة كـ`RESOLVED/CHANGED/CANNOT_REPRODUCE` بدليل.

### المرحلة 8 — CI، ترحيل، staging، وإعلان الجاهزية (`S23–S26`)

**العمل:** `S23–S24` أغلقت lockfiles/readiness/CI/strict E2E/Docker/security بحسب تقارير التنفيذ. المتبقي في هذه المرحلة الآن هو `S25–S26`.

في `S25` شغّل fault injection وإعادة تدقيق على **المعمارية بعد S24.5**، وتشمل على الأقل: kill أثناء materialize/render/upload، موت API، موت worker وانتهاء lease، PostgreSQL outage/reconnect، StorageService/S3 outage، partial output upload، فساد/stale artifact، writer متزامن، cross-tenant reference، وإعادة الاستئناف دون double publish أو تقدم زائف.

**الهجرة والإطلاق بعد S24.5:**

1. لا توجد migration لمشاريع المستخدمين القديمة؛ البيانات الحالية تجريبية. ركز على schema migrations versioned/idempotent وقابلية إنشاء بيئة نظيفة من الصفر.
2. نفّذ staging على PostgreSQL حقيقي وS3-compatible backend فعلي/محاكى بصدق، لا SQLite/Local فقط.
3. اختبر backup/restore لقاعدة البيانات وobject storage metadata، وحدد RPO/RTO قبل production.
4. نفّذ load/soak لعدة workspaces ومشاريع متزامنة، مع إنذار worker outage وqueue backlog وDB/storage failures.
5. pilot محدود بمشاريع جديدة، ومراجعة logs/metrics/QC والعزل بين المستأجرين.
6. Final Architecture Re-Audit مستقل: authorities، transitions، artifact graph، tenant isolation، PostgreSQL، StorageService، Local/Docker، API. أغلق findings في ledger فقط بدليل red/green وPR/CI.
7. `S26`: فعّل ruleset النهائية وrequired checks ومنع direct/force push مع دليل رفض فعلي.

**بوابة الخروج:** القواعد فعالة على `main`، إعادة الإنتاج القديمة تمر كاختبار انحدار، اختبارات restart/backup/restore موثقة، ولا P0 مفتوحة ولا P1 غير مقبولة صراحة. الاختلاف `needs verification` مثل انقسام JS toolchain يحسم باختبار وقرار، لا بتخمين.

|---|---|---|

| `approved_by` مزور أو approval على Blueprint قديمة | رفض، review bundle وprincipal موثقين | 1–2 |

| Manifest فيه ID مكرر/هوية مشروع مختلفة | schema/semantic failure قبل أي I/O | 3 |
| أصل صحيح وآخر مفقود أثناء materialize | لا map ولا public generation جزئية | 4 |

| انقطاع PostgreSQL أثناء transition أو lease renewal | لا تقدم جزئي؛ recovery/rollback معلوم ولا lost update | 9 / S25 |

## 5. شروط Go / No-Go للإنتاج

قرار `GO` يحتاج محضرًا يذكر SHA الإصدار، migrations، أسماء CI المطلوبة، نتائج staging/pilot، وسعة النشر المعتمدة. جميع الشروط التالية إلزامية للهدف الإنتاجي المختار:

1. صفر P0 مفتوحة، وصفر P1 دون قبول واعٍ مسجل بمالك ومبرر وتاريخ مراجعة.
2. لكل finding مثبتة اختبار أحمر محفوظ واختبار أخضر ومرجع PR/CI في ledger.
3. لا مسار مباشر لتعديل lifecycle أو approval دون authority.
4. state/evidence/revision ذرية، وCAS/lease تمنع ضياع التحديثات.
5. required evidence/invalidation تعطي الحكم نفسه عند التنفيذ والاسترداد.
6. العقود وproject/template/asset IDs واحدة عبر Python وTypeScript والRuntime.
7. traversal وduplicate IDs وunknown refs وstale public files تفشل مغلقًا.
8. review bundle تربط الهوية بالمدخلات والمخرجات التي رآها الإنسان، وتُبطل إذا تغيّرت.
9. materialization والنشر قابلان للمصالحة بعد crash بلا نجاح جزئي.
10. Local/Docker/Studio/Probe تتلقى نفس render input.
11. strict E2E بلا bypass، بثلاث نسب أبعاد وصوت وميديا وقوالب متعددة.
12. فشل أداة QC الحرجة يعطي فشلًا معلنًا، وFinal QC على الفيديو الناتج.
13. API محمية عند النشر الشبكي، وملفات upload/download مفوضة ومحدودة.
13.1. كل Project مرتبطة بـWorkspace غير فارغة، وكل access يمر بتفويض tenant-scoped.
13.2. PostgreSQL/leases/CAS هي authority الإنتاجية للحالة والوظائف، ولا تعتمد الحقيقة على process-local locks.
13.3. StorageService هي boundary التخزين الدائم، وcross-tenant object references مرفوضة.
13.4. worker filesystem مؤقتة وقابلة للمسح دون فقدان state/output الدائم.
14. jobs/events/cancellation دائمة وتنجو من restart.
15. GUI تستطيع إدارة المشروع والأصل والموافقة والتقارير والفيديو عبر API.
16. dependencies locked، Docker image معروفة النسخة، ولا pip install عند التشغيل.
17. CI/required checks تشمل Python وTS وcontracts وDocker وsecurity وstrict E2E.
18. `main` محمية بقواعد فعالة مثبتة بتجربة رفض تغيير غير مستوفٍ.
19. readiness/metrics/logs/backups/restore وalerting مجرّبة على staging وفق أهداف متفق عليها.
20. Final Architecture Re-Audit لا تعيد فتح root cause، ومالك المنتج/التشغيل يوقعان قرار الإطلاق.

إذا فشل شرط واحد فلا يُعلن النظام production ready؛ يمكن إطلاق pilot مغلق مع مخاطر مسجلة فقط إذا لم توجد ثغرة ثقة أو سلامة بيانات حرجة.

## 6. إدارة التنفيذ والملكية

- **مالك التغيير:** لكل PR مالك هندسي واحد ومراجع واحد؛ أي تعديل للعقود يحتاج مراجعة Python وTS.
- **مالك القرار:** صاحب المنتج يقر سياسة QC وأدوار الموافقة ومتطلبات GUI؛ المسؤول التشغيلي يقر backup/RPO/RTO/alerts ونمط النشر؛ مسؤول الأمن يراجع auth/path/upload/subprocess.
- **مراجعة أسبوعية:** عدد البنود المؤكدة والمغلقة حسب P0/P1، حالات blocked، آخر تجربة recovery، تغطية مسارات Local/Docker، وقرارات العقود المتبقية. ليست «نسبة إنجاز» بلا دليل.
- **قاعدة PR:** رابط finding، red reproduction، diff العقد والـmigration، green test، أثر rollback، ونتيجة CI. تغييرات الوثائق تلي تغيير السلوك وتصف المنفّذ ونقطة التنفيذ.
- **تنسيق العمل المتوازي:** Python state/security وTS registry يمكن أن يتقدما في فروع منفصلة بعد قرار العقد؛ materializer ينتظر Manifest v2؛ API write services تنتظر Lifecycle/Artifact services؛ Full E2E ينتظر التكامل. لا تُحسم merge conflicts بإعادة إدخال legacy behavior.

### تقدير التخطيط

لم تتوفر سعة الفريق أو شكل النشر أو نتائج إعادة التحقق؛ لذلك لا تُعد هذه الخطة وعدًا بتاريخ إطلاق. بعد `S00` يُقدّر كل commit بحجم العمل والاختبار والهجرة، وتوضع له نافذة تنفيذ. المسار الحرج المنجز حتى الآن هو: **التحقق → حدود الثقة → الحالة/المراجعة → العقود → الوسائط والقوالب → الرندر/QC → API/jobs → CI → SaaS foundation**. المتبقي لهذه الخطة: **S25 fault injection/re-audit → S26 governance closure**. يمكن ضغط الزمن بموازاة القوالب والوسائط بعد قفل العقود، ولا يمكن اختصار اختبارات الانقطاع والترحيل والنسخ الاحتياطي دون تغيير تعريف الجاهزية.

## 7. طريقة قراءة هذه الخارطة مع السجل

هذا المستند يرتب قرارات التنفيذ وبوابات العبور. مصنف **Master Remediation Ledger** يبقى سجل الحقيقة للبنود الـ92. أضيفت `S24.5` كحزمة معمارية بلا Findings تاريخية جديدة، لذلك لا تُغلق صفوف السجل تلقائيًا بسبب نجاحها. في `S25` يعاد تصنيف البنود المتأثرة وإرفاق red/green/CI/PR لكل بند قبل اعتباره مغلقًا.
